## 2026-09-23: クラウドで Jev に切り替わらない不具合の調査と、価格表の中身を CDK から外す（決定64）

### 調査で分かったこと

- AppConfig では配信 #6（版 7、本日 18:14 JST に CDK の外で配信）で `judge: "jev"`（目安 6,500 / 10,000 / 14,000）が配られていた
- CloudWatch に「[pricing] 判定器の指定を読み取れませんでした（"jev"）。bedrock を使います」が出ていた（本日 18:18 JST 以降）
- Jev の鍵（Secrets Manager）は投入済みで、仮の値ではなかった
- 出力 `Price`・環境変数 `PRICE`・AppConfig の読み取り権限 `*` も残っており、9/21 の deploy 以降のコミットは何も反映されていなかった
- 別件: 本日 2 回、Haiku の答えから価格帯を読めず竹に落ちていた（「段を読み取れなかったため既定の段に落とします」、18:15 と 18:19 JST）。
  「jev の判定がおかしい」と見えた一因かもしれない。原因は未調査

### 判断

- 直すには deploy し直せばよい。ただし CDK が既定の表を中身に持つ版と配信を作っており、既定値を書き換えたコード（`bedrock` → `haiku`）を
  deploy すると、人が入れた表が既定値に戻る。ユーザーが、AppConfig を上書きしない deploy の仕組みを求めた
- 案の変遷（以下、AppConfig の Application / Environment / ConfigurationProfile / DeploymentStrategy を「器」、
  版と配信を「中身」と呼ぶ）: ①器ごと CDK の外で作る（最初の提案）→ 初回の手間が増えるとしてユーザーが退けた。②中身だけ別スタックに分ける（ユーザー提案）
  → スタック間の参照があると `cdk deploy <本体>` が参照先も自動で deploy するため、`--exclusively` の付け忘れに頼る形になる。名前で渡して
  参照を切ると、IAM の読み取り権限を広げることになる。この 2 点を示して退けた。③器は CDK、中身は CDK の外（ユーザーが挙げ、採用）。
  `pnpm set:jev-key` と同じ形で、初回は何もしなくても既定の表で動く
- `set-tier-table.ts` での入力の検証は、JSON であることと `tiers` を含むことだけにした。サーバーの `parseTierTable` を import すると、
  パッケージの境界（server は ESM の別パッケージ）を跨ぐうえ、検証を二か所に持つことになる。`tiers` だけは見る。`{"judge":"jev"}` だけを
  配ると表ごと退けられ、切り替えたつもりで何も変わらないため

- `tiers`: `parseTierTable` で価格の順序と 0 ドルを検める
- `quote` / `app`: 判定モデルの確信度を 402 のログへ運ぶ
- `judge-guard` / `app`: コメントの U12 を決定57 へ直す（昇格済みのため）

### 判断

- 読み取りの寛容化は、失敗が静かに価格へ効くため。完全一致だと `take。` 程度の飾りで
  中央の価格帯へ落ち、警告 1 行しか残らない。語が複数混じれば「選べていない」とみなして
  落とすので、寛容にしても曖昧な答えを拾い上げてしまうことはない
- 前置きの共有は、Bedrock 側にだけ実測由来の一文が入っていて土台が揃っていなかったため。
  docs が `instructions` にオブジェクトを許し、問いと前置きを別の欄に分ける書き方を
  推奨しているので、`{ question, context }` の形にした
- 確信度は記録だけに使い、閾値で分岐させない。score は水準の期待値なので、判定が割れる
  ほど値は中央へ寄って竹に着地する。迷いは何もしなくてもフォールバック先へ流れる
- 見送ったもの: 人手へのエスカレーション（無認証の自動売買で人が介在しない）、
  依頼文→価格帯の短期メモ化（`extra` は実測で往復しており、ステートレスを濁す割に得が薄い）、
  Bedrock 経路の tool use 化（読み取りの寛容化で実害が消え、お試し実装には過剰）

### つまずき

- `readTier` を素朴な部分文字列の照合にすると `document` が `ume` に当たる。語の
  切れ目（`\b`）で拾うようにして避けた
- 評価セット（`eval-cases.test.ts`）は converse も fetch も差し替えており、ヘッダーが
  謳う「全価格帯が同じ答えに潰れる事故を捕まえる」は実モデルに対しては果たせていない。
  実モデルを環境変数で開く案は今回見送り。次に判定の文言を触るときの課題として残す

### セルフレビューでの手当て

上の変更を self-review にかけ、6 件を直した。

- `scoreToTier` が NaN で `Tier` を名乗る undefined を返していた（`TIER_ORDER[NaN]`）。
  旧実装は NaN でも松を返していたので、一般化の副産物として堅牢性が後退していた。
  有限でない値は中央の価格帯へ収める

  入力と期待する価格帯の組にして価格帯そのものを検める

- 評価セットのヘッダーが果たせない約束を述べていたので、実態に合わせた

## 2026-09-20: 売り手の値付けの見直し（Jev の調査と、動的見積もり + upto 併記の方針）

検討のみ。実装には入っていない。

### やったこと

- ユーザーから「Jev で売り手側の高速化とコスト削減ができないか」と相談を受け、一次情報まで
  当たって調査した（TypeSafe AI の公式ドキュメント・gihyo・MarkTechPost・Vercel AI Gateway）
- 売り手の原価構造を確認した。有料ツールは `generate-html` だけで、費用も時間もその実質すべてが
  Bedrock の Converse 1 回（`maxTokens` 64,000）に集中している。買い手は `modelId` を送っていないため、
  常に既定の Sonnet 4.6 が使われており、`ALLOWED_MODEL_IDS` の Opus は実際には選ばれていない
- x402 の上流実装を読み、呼び出しごとの値付けが成立するかを確かめた（`@x402/mcp` の
  `createPaymentWrapper`、`@x402/core` の `findMatchingRequirements` と `SettlementOverrides`、
  `@x402/evm` の `upto` スキーム）
- x402.org の facilitator の `/supported` を叩き、Base Sepolia で `upto` が広告されていることを実測した
- 決定53・54 を起こし、U10・U11 を起票した。決定18・21 には追記で経緯を残した

### 調査で分かった重要事実

- Jev は型付きの判断だけを返すモデル。Noul / Choice / Score の 3 種で、入力 $0.042/1M・出力無料、
  応答 70〜500ms、テキスト専用。Bedrock では提供されず早期アクセス（waitlist）。「ハルシネーションなし」は
  スキーマ適合の保証であって判断を誤らないという意味ではないと、開発元自身が明記している
- `@x402/mcp` の公開されている `createPaymentWrapper` は `accepts` を構築時に固定で受ける。
  `DynamicPrice` 型は存在するが既定の経路には繋がっておらず、呼び出しごとに価格を変えるには自前で
  accepts を組む必要がある。当サンプルはリクエストごとにサーバーを組み直す（決定22）ため、
  本文を先に読む改造を入れれば成立する
- x402 v2 の要件照合は「サーバーが宣言した要件がすべて一致すること」を求める。
  見積額が 2 往復でぶれると買い手が 402 を受け取り続ける（U11）
- `@x402/evm` に `upto` スキーム（Permit2 専用）がある。README が「LLM のトークン生成のような
  変動費のエンドポイントに最適」と名指ししており、`amount` に `"0"` を渡すとオンチェーンの決済自体を
  行わない。すなわち課金しない
- x402.org の facilitator は Base Sepolia で `exact` / `upto` / `batch-settlement` に対応し、
  gas 肩代わりの拡張（`eip2612GasSponsoring` / `erc20ApprovalGasSponsoring`）も広告している

### 判断・つまずき

- 当初、Jev の置き場として「支払い前に依頼の実現可能性を判定する門番」を提案したが、ユーザー指摘で
  取り下げた。upfront（決定21）で損を被るのは買い手であり、その判断を売り手に置くのは、損をしない者に
  損の判断を委ねる形になる。売り手には「満たせる」と答える誘因しかない
- ユーザーの「むしろ判断すべきは売値では」という指摘で、値付けこそが正しい置き場だと分かった。
  ただし判定モデルとしての Jev の優位（0.1 秒・$0.00002）は、$0.1 の取引と 600 秒の処理予算に対して
  誤差であり、AWS の外へ出る代償に見合わない（決定53）
- `upto` を見つけた際に「実費で請求すれば見積もりは要らない」と結論しかけたが、ユーザー指摘により
  誤りと認めた。値付けの方針（事前に額を提示するか、後から実績で請求するか）と決済の機構
  （`exact` か `upto` か）は直交する別の軸で、実費請求は買い手が検証できない額を売り手が一方的に
  決める形になる
- 最終的な方針はユーザーの案による。Haiku の見積もりを上限として提示し、`upto` が使える買い手には
  割り引き、使えない買い手には満額請求し、超過は売り手が被る（決定54）

### U10 の検証（同日）

`upto` を AgentCore Payments が署名できるかを、ap-southeast-1 で実際に試した。CLI に
`aws bedrock-agentcore process-payment` があるため、依存の導入なしに投げられた。

- 手順: 読み取り専用の一覧 API で PaymentManager・Connector・Instrument を引き（`.env` は不要だった。
  userId は `payments-setup.ts` の既定である `sample-user-1`）、枠 $0.05・期限 15 分の PaymentSession を
  切って、`scheme: "upto"` の支払い条件を 1 回だけ投げた。金額は $0.01、宛先は買い手自身のウォレット、
  `extra.facilitatorAddress` には x402.org facilitator の `/supported` が返す署名者アドレスを入れた
- **結果: 署名できる**。`PROOF_GENERATED` が返り、`permit2Authorization` を得た。witness に `facilitator`
  と `to`、`permitted.amount` に提示額、`spender` に upto のプロキシ契約が入っている。U10 は決着
- 併せて分かったこと: 署名の時点で PaymentSession の枠が上限額で消費される（$0.05 の枠が $0.04 に
  なった）。決済は起きていないのに戻らず、データプレーンのコマンド一覧にも決済結果を通知する API は
  無い。`upto` で割り引いても買い手の枠は上限額のまま減る（決定54 に追記）
- 後片付け: 検証用の PaymentSession は削除した。オンチェーンの送金は発生していない
  （証明を facilitator へ渡していないため、決済は成立していない）

### U11 の設計（同日）

見積額を 402 応答と支払い呼び出しで一致させる方法を、上流の実装を読んで詰めた。結論は
決定55（HMAC で封じた見積書を `extra.quote` に載せる）。読んで確かめたのは次の三点。

- 照合規則: `paymentRequirementsMatchAccepted` は `amount` を含む core フィールドを `deepEqual` で
  突き合わせ、`extra` は「売り手の要求が買い手の申告の部分集合であること」を求める
  （`dynamicExtraFields` は除外）。見積額を 2 往復で再現できなければ、買い手は 402 を受け取り続ける
- `extra` の合成: `buildPaymentRequirements` は `...parsedPrice.extra, ...resourceConfig.extra` の順で
  合成し、呼び出し側が渡した鍵を残す。スキーム固有の付加（`upto` の `facilitatorAddress` など）は
  その後に載る。封を置く余地がある
- 買い手の返し方: `x402-payer.ts` は ProcessPayment の結果を包み直す際、`accepted` を受け取ったまま
  返している。封は無傷で往復する。ただし「ProcessPayment が完全な PaymentPayload を返した場合は
  それをそのまま使う」分岐があり、その経路では封の保存が AgentCore 側の挙動次第になる。
  U10 の実測では内側の署名ペイロードのみが返り、この分岐には入らなかった

保存先を持つ案（引数のハッシュから見積額を引く表）は、ステートレス（決定22）を崩し資源も増えるため
採らなかった。有効期限を 15 分と長めに取るのは、決定31・48 の人の承認で買い手が待つ経路があり、
短いと承認の間に失効して買えなくなるため。

設計の副産物として U12 を起票した。402 を返す経路が Haiku の呼び出しを伴うようになるため、
無認証の公開エンドポイント（決定19）では、支払う気のない相手が見積もりだけを繰り返して売り手に
費用を負わせられる。U9 と同種の経路が一つ増える。引数の大きさによる決定的な足切りを Haiku の手前に
置く案を書いた。

なお U11 のテスト（見積額がぶれた場合、安い見積書を高い依頼に付け替える細工）は、値付けの実装と
同時に書く。先にテストだけ書いても対象が無いため。

### ローカルの System One 実装の比較と、値付けの前提の崩壊（同日）

決定53 で Jev を見送った理由が「速度と費用の差がこの取引規模では効かない」だったため、判定が
4 択（後に 3 択）に軽くなった時点で前提が変わる、というユーザー指摘を受けて測り直した。

#### 測ったもの

評価セットは、`generate-html` に来る想定の日本語の依頼文 20 件。当初のラベルは筆者が目分量で
付けた 4 つの価格帯（small / medium / large / xlarge）。

| 判定モデル | 規模 | 日本語 choice | 英語 choice | 英語 score | 速度 |
| --- | --- | --- | --- | --- | --- |
| LFM2.5-1.2B | 1.2B | 9/20 | 10/20 | 11/20 | 195ms |
| ModernBERT-ja-jev | 310M | 9/20 | 9/20 | 11/20 | 125ms |
| TinySwallow | 1.5B | 6/20 | 8/20 | 12/20 | 272ms |
| Qwen2.5-1.5B | 1.5B | 12/20 | 10/20 | **15/20** | 239ms |
| Qwen3-1.7B | 1.7B | — | — | 測定不能 | — |
| Haiku 4.5（定義文を改めた版） | — | — | — | 19/20 | 1,037ms |

いずれも `Argos1111/jev_local` の `/v1/systemone` 互換サーバー経由。基盤の差し替えは、別ポートに
llama-server を立てて `api_server.py --backend-url` を向け替えることで行った。

#### 分かったこと

- **判定の形は score が一貫して最良**。5 つの基盤すべてで choice より score が上回った
- **criteria の言語が効く**。英語にすると LFM の score が 7/20 → 11/20 に改善し、群平均の単調性も
  回復した。英語で学習された基盤には判定の枠組みも英語で与えるほうが素直に効く
- **日本語特化の蒸留が効くとは限らない**。TinySwallow（12/20）は素の Qwen2.5-1.5B（15/20）を下回った
- **思考モデルは構造的に噛み合わない**。Qwen3 は応答の先頭が `<think>` になるため、先頭トークンの
  確率を選択肢に割り振る方式では確率がそこへ吸われる。`jev_local` に `--empty-think` があるが
  `api_server.py` には露出していない。5/20 は「弱い」ではなく「測れていない」
- **System One の枠組みは小型モデルほど有用**。同じ定義文を素の生成プロンプトで LFM に与えると
  6/20 まで落ち、20 件中 8 件は価格帯の語すら取り出せなかった（criteria の鸚鵡返し、HTML を書き始める、
  「3」とだけ返す）。スキーマ適合の保証は、形式指示に従えないモデルと組むときにこそ効く
- 変種の異なる 2 問の max を採る規則で 18/20 まで伸びたが、閾値も組み合わせ方も同じ 20 件を見て
  決めており過学習

#### 評価セットを実測に置き換えたら、前提が崩れた

ラベルが筆者の主観である限り、測っているのは「筆者の直感との一致」でしかない。そこで新しい
依頼文 20 件を Haiku に生成させ、売り手の既定モデル（Sonnet 4.6）と実際のシステムプロンプトで
生成させて出力トークン数を実測し、それを正解にした。

- 実測の分布は 3,374〜13,378 トークン（中央 6,569、幅 4.0 倍）。原価にして $0.05〜$0.20、中央値 $0.10
- 決定18 の固定価格 $0.1 は、実測の原価中央値とほぼ一致していた
- **依頼文から出力量は予測できない**。実測ラベルに対する Haiku の的中は 10/20 で、最頻クラスだけを
  答える基準線 9/20 とほぼ同じ。20 件中 14 件を真ん中の価格帯と答えており、判別できていない

つまり、それまでに報告した的中率（Haiku 19/20、ローカル 18/20）はすべて主観ラベルへの一致率で

#### 予測から制御への転換（決定56）

予測できないなら決めてしまえばよい、というユーザーの提案で設計を変えた。価格帯を判定したら、その価格帯の
目安トークン数を生成時の指示に織り込む。

追従するかを実測した（3 依頼 × 3 つの価格帯）。

| 依頼（元の実測） | 梅 5,000 指示 | 竹 8,000 指示 | 松 12,000 指示 |
| --- | --- | --- | --- |
| 時間割表（3,374） | 4,871 | 8,426 | 9,242 |
| スコアランキング（8,580） | 5,729 | 8,946 | 9,463 |
| 授業予約サイト（13,378） | 6,256 | 9,980 | 14,316 |

9 点すべてで順序が保たれ、打ち切りは 0 件。目安は引き寄せる力であって固定する力ではなく、軽い
依頼に松を指示しても 9,000 台で頭打ちになるが、軽い依頼を松と判定すること自体が判定の誤りなので
実害はない（ユーザー判断）。

この転換により、判定モデルの仕事は「モデルが何トークン書くかを当てる」から「依頼に見合う規模を
判定する」に変わる。後者は主観ラベルで測っていたものと同じであり、Haiku 19/20・ローカル 15〜18/20 と
いう数字が改めて意味を持ち直す。

## 2026-09-07: セキュリティ点検 — 売り手の「402 だけで守る」構えの評価

### 発端

ユーザーの依頼「全体的なセキュリティチェックを。特に売り手が 402 だけで制限をかけている
ところにどの程度リスクがあるか、穴があるならどの程度塞げるのか、どこまで対応すべきかを
整理しておきたい。薄利多売になる性質上、お金を払ったかどうか以外はなるべくオープンに
するべきだと思うが、それだとどの程度リスクがあるのか」。

### 実測したこと

偽 facilitator（`server/src/testing/fake-facilitator.ts`）を使い、一時的な検証テストで
往復を数えた（テストは点検後に削除。恒久版は下記の「やったこと」に残した）。

- `initialize` / `tools/list` / `resources/read`（無支払い）… facilitator 0 回、Bedrock 0 回
- `tools/call`（無支払い）… facilitator 0 回、Bedrock 0 回。支払い要求を返すだけ
- `tools/call`（`accepted` ブロックが合わない）… facilitator 0 回。上流が `No matching payment requirements` で弾く
- `tools/call`（`accepted` は合うが authorization を壊した）… **`/settle` が毎回走った**
- upfront では `/verify` は呼ばれず `/settle` のみ

壊したのは 5 パターン（有効期限切れ・有効期間の開始前・金額不足・宛先すり替え・
署名が `0xdead`）で、いずれも facilitator まで到達した。つまり `@x402/mcp` 2.24 の
`createPaymentWrapper` は、買い手がエコーバックする `accepted` しか照合しておらず、
`payload.authorization` の中身は一切見ていない。

別の探りとして、正規ペイロードをそのまま**再送**した場合も毎回 `/settle` が走ることを
確かめた（売り手側に nonce の台帳が無い）。これは上の 5 パターンとは別の経路で、
今回の門番では止まらない。真のリプレイはオンチェーンの nonce 消費で失敗するため
二重に課金されることはないが、settle 往復そのものは発生し続ける。

### 評価

- **402 単独のゲートは認可としては正しく働いている。** 未払いの呼び出しは Bedrock に届かない
  （`x402-flow.test.ts` の既存テストと今回の実測の両方で確認）。決定21 の upfront は狙いどおり
- 原価には上限が無い。`maxTokens` が 64,000、`modelId` を買い手が Opus 4.8 まで選べて価格は同一、
  `previousHtml` に `.max()` が無い。買い手が売り手の Bedrock 費用を大きく動かせる
- **当初は「価格が原価を賄っていない」と整理したが、これは誤り**（ユーザーの指摘で 2026-09-07 に訂正）。
  収入は Base Sepolia のテスト USDC（$0）で、原価だけが実費の Bedrock ドルなので、
  「価格 ≥ 最悪原価」という不等式は破れているのではなく**成立しない**。`PRICE` にどんな値を
  入れても満たされず、faucet の供給が 1 回 1 USDC ずつである以上、上げる意味も無い。
  上に挙げた 3 点は値付けの誤りではなく「原価に上限が無いこと」として扱う。
  この不等式が本当の制約になるのは mainnet で実資産を受け取る場合に限る
- **訂正しても残る、むしろ鋭い言い方**: 攻撃者は何も壊す必要が無い。faucet で受け取り、正規に支払い、

### セルフレビューでの訂正 — 門番は謳った穴を塞げていなかった

PR #26 に 8 観点の機械レビューを掛けたところ、設計・セキュリティ観点から「門番は迂回できる」と
指摘された。鵜呑みにせず自分で実測して確認した結果、指摘は正しかった。

攻撃者はウォレットも資金も一度の正規購入も要らない。

1. 無支払いで `tools/call` を叩き、402 応答から `accepts` をタダで手に入れる
   （`{"scheme":"exact","amount":"100000","payTo":"0x…","extra":{…}}` がそのまま返る）
2. それを `accepted` に丸ごと転記する。上流の `deepEqual` は必ず一致する
3. `authorization` の宛先・金額・有効期間を条件どおりに手書きする
4. 署名欄に `0x` + 任意の 130 桁 16 進数を入れる

これで門番を通過し `/settle` に到達した。原因は upfront では上流が `/verify` を呼ばないことで、
署名が実際に検証されるのは facilitator の `/settle` だけになる。その手前にある唯一のゲートが
「130 桁の 16 進数か」という形式検査では、素通りして当然だった。

つまり門番が弾けるのは「攻撃者がわざわざ選ぶ理由の無い壊れ方」だけで、**掲げた脅威は未解消**。
実際に塞ぐ手は U9 の EIP-712 署名復元しかない。

見落とした直接の原因も記録しておく。最初の手書きペイロードが `accepted` 不一致で止まったところで
「手書きは通らない」と早合点し、「`accepted` も 402 応答からコピーすればよい」という一歩を踏まなかった。
統合テストも `capturePaymentPayload()` で必ず一度実クライアントに買わせてから 1 箇所壊す形しか組んでおらず、
実際の脅威モデル（一度も支払わず全項目を手書きする）を一度も試していなかった。この死角がそのまま
PR 本文・DESIGN.md・本記録の「攻撃者は正規の支払いを 1 度買う必要があるぶん敷居は上がる」という
誤った記述を生んだ。

- **ユーザー判断（2026-09-07）**: 門番は取り下げず、軽量な入力検証として残す。ただし主張は格下げし、
  穴が開いたままであることを PR 本文・U9・本記録に明記する
- `x402-flow.test.ts` に「【未対応・U9】一度も支払わずに捏造したペイロードは門番を通過して settle まで届く」を
  足し、限界を実行可能な形で残した。U9 を塞いだときにこのテストが落ちるので、そこで期待値を書き換える

同じレビューで出た他の指摘も直した。

- `payment-guard.ts` の「拒否を支払い要求の形で返さない」理由の引用先が誤っていた。`agent-app` の

### 見送ったもの（U9・Tier 2 として記録）

- **EIP-712 署名そのもののローカル復元**（U9 に起票）。**settle 往復の濫用を実際に塞げる唯一の手**で、
  今回入れた門番はこれの代わりにならない（後述の訂正の節を参照）。見送った理由は、
  スマートコントラクトウォレット（ERC-1271 / 6492）の正当な支払いを弾く恐れがあり、
  本サンプルの買い手が EOA かどうかが未確認のため。次の実決済で `authorization.from` を実測してから決める
- payer アドレスを identity にしたクォータ / ブロックリスト。支払い済みの相手にしか出ない
  擬似識別子で、アカウントも API キーも足さずに乱用へ対処できる、オープン性と両立する筋。
  ただし「1 回 $0.1 という Sybil コストが構造的に備わる」という当初の見立ては**テストネットでは成り立たない**
  （2026-09-07 訂正）。faucet の USDC は無料なので、アドレスを増やす費用はゼロ。
  効いているのは faucet 自身のレート制限であって x402 の防御ではない。
  Sybil 耐性が備わるのは mainnet で実資産を払う場合に限る
- Bedrock Guardrails。無認証・無審査の LLM 出力が売り手の AWS アカウントの下で生成されるため、
  AUP 上の責任は口座主に向く。値付けの調整では届かない領域
- AWS Budgets のアラーム（`reservedConcurrency` が累積コストの上限にならないことへの手当て）
- settle レシートのオンチェーン確認。売り手は facilitator の `success: true` を無条件に信じている
  （偽 facilitator で実証）。x402.org は API キー不要で使える代わりに信頼点になっている

  `pnpm` / `npx` が動かなかった。`MISE_TRUSTED_CONFIG_PATHS` を環境変数で渡して回避した

- ユーザーの申し出「トップページ以外の適当なパスでもアプリが動く。購入した HTML に変なものを仕込まれたときに困るので 404 にしたい」
- 調べた結果、コードではなく配信層の挙動だった。クラウドは Amplify コンソールがアプリ作成時に自動で付けた
  `/<*> → /index.html (404-200)` の規則（`aws amplify list-apps` の `customRules` で実物を確認）、
  ローカルは Vite 既定の `appType: 'spa'` のフォールバック（Blocks の開発サーバーは API 以外を Vite にそのまま流す）
- 危険度の見立て: 購入 HTML は不透明オリジンの sandbox iframe に閉じているので、フォールバック自体が権限を増やすわけではない。
  それでも任意 URL が本体を 200 で返すのは不要な露出で、この画面はクライアントルーティングを使わないため締めても失うものが無い

### やったこと

- `agent-app/vite.config.ts`: `appType: 'mpa'`。開発サーバー・preview とも存在しないパスは 404
- `agent-app/public/404.html`: 体裁用の自己完結の一枚（外部 CSS・JS 無し）。Vite が `dist/` 直下へ写す
- Amplify アプリ（ap-northeast-1、`dei96o54khd9a`）の規則を `/<*> → /404.html (404)` に差し替えた（`aws amplify update-app`）。
  アプリ単位の設定でリポジトリでは管理できないため、README のクラウド deploy 節に手順を書いた
- DESIGN.md に決定45

### セルフレビューで見つかった誤り（同日）

- **CDK 直 deploy の経路を「変更不要」と誤って結論していた。** 決定45 の初版は「`Hosting` は `spaFallback` 既定 false」と書いたが、
  根拠にした `?? false` は CloudFront Function を組み立てる低層（`@aws-blocks/hosting` の `defaults.js`）の既定で、
  実際にそこへ渡る値はアダプタが決めていた。`detectFramework` は next / nitro / astro / sveltekit 以外を全て `'spa'` に落とすため
  （`adapters/index.js`）、この Vite プロジェクトは `'spa'` 判定 → `spaFallback: true`。`npm run deploy`（決定33 の退路）では
  今も任意パスがアプリ本体を 200 で返す状態だった。既定値が多層のとき、低層の既定を見て早合点したのが原因
- 直し方: `aws-blocks/index.cdk.ts` の `Hosting` に `framework: 'static'` を明示。あわせて SPA アダプタが `dist/404.html` を見て
  `errorPages[404]` に自動配線するので（`adapters/spa.js`）、追加した `public/404.html` が CDK 経路でもそのまま効く
- Amplify の規則がリポジトリ外の手動設定である件は、`amplify.yml` から `update-app` を流す案の副作用（サービスロールに
  `amplify:UpdateApp` が要る・ビルドがアプリ設定を書き換える）を嫌って手動運用のままとし、残存リスクを決定45 に明記した

### 検証・つまずき

- クラウドの実応答は main ブランチにアクセス制御（Basic 認証）が掛かっており、curl では全パスが 401 だった。
  規則の反映は `update-app` の応答で確認し、404 ページ自体は本ブランチが deploy されてから（`404.html` が `dist/` に入ってから）
  ブラウザで確認する。規則の差し替えは deploy 前でも害はない（無いファイルは元から Amplify 既定の 404 になる）

## 2026-09-05: 買い手の画面を Pico.css で整える（決定41）

### 着工前の詰め（grill-me）で決めたこと

- 「UI が分かりづらい」→ 直すのは **見た目だけ** 。デバッグ用の表示（直近コード・イベントログ・会話 ID）は
  情報設計ごと現状維持、というユーザー選択。対象は `index.html` の 3 区画すべて
- 手段は軽量な classless CSS フレームワーク（Pico.css）。読み込みは CDN 直読みではなく npm 依存
  （他の依存の管理方針に合わせ、オフラインでも動くため）

### やったこと

- `@picocss/pico` 2.1.1 を追加し、`src/style.css` を新設（`pico.blue.min.css` を `@import` し、
  淡いブルーのテーマ変数と独自要素のスタイルを重ねる）。`index.html` の `<style>` は撤去して `<link>` に
- マークアップを Pico の作法に寄せた: `main.container` / `article` + `header` のカード / チャット入力は
  `role="group"` 。`viewport` の meta を足し、見出しは `h2` のまま残して意味づけを壊さないようにした
- ID とクラス名（`msg` `interrupt` `purchase` `signed-in-only` など `src/index.ts` が触るもの）は据え置き

### つまずき・判断

- `role="group"` の中は子が等分に伸びるため、ボタンだけ `flex: 0 0 auto` にした
- テーマ変数を素の `:root` に置くと Pico の `:root:not([data-theme=dark])` に負けて効かない。同じ強さの
  セレクタで後に書いて上書きした
- 暗色環境で崩れるのを避けるため `data-theme="light"` を固定した。独自要素の吹き出し・ログが明色前提で、
  自動切替に任せると白い箱に白い文字になる
- Authenticator は自前のカード枠を inline style で描くため、`article` と枠が二重になる。inline style が
  相手なので `!important` で打ち消した
- 淡い色を primary に使うと白抜き文字とのコントラストが落ちるので、primary は `#2c6fb0`（白に対して 5.24:1）に
  留め、淡さは背景・枠線・吹き出しで出した
- 390px で 「直近のコードを表示」 のボタンが 3 行に潰れていた。横並びの行（`.code-hint` `.interrupt`
  `.purchase`）に `flex-wrap: wrap` を足し、チャット入力は 576px 以下で枠線の連結をやめて入力欄を 1 行、
  ボタンをその下に並べるようにした
- セルフレビューで 3 件直した。①Pico の `.container` は 1280px 以上で 1200px、1536px 以上で 1450px まで
  広がり、会話の一行が長くなりすぎるので旧実装と同じ 960px で頭打ちにした
  ②`.msg` に `overflow-wrap: anywhere` を足した（tx ハッシュのような空白を含まない長い文字列で
  吹き出しがはみ出す。旧実装から在る穴だが、`#chat-log` を面にして目立つようになった）
  ③購入一覧の「まだありません」は、JS の再描画で class の無い span になり初期表示と見た目が変わるため、
  muted に揃えた

### PR レビュー（PR #11）で出た指摘と対応

**セルフレビューで「直した」2 件が、実は詳細度で効いていなかった。** 見た目の確認をスクリーンショットだけで
済ませたのが原因で、CSS は「当たっているか」を計算値で測らないと分からない。今回は Playwright で
`getComputedStyle` を取って裏を取った。

- `body > main`（0,0,2）は Pico の `.container`（0,1,0）に負ける。1920px で `max-width` の実測値は 1450px で、
  頭打ちがまったく効いていなかった。`body > main.container` に直した
- `#purchases > span`（1,0,1）は `.error`（0,1,0）に勝つので、購入一覧の取得失敗（`showError`）の警告が
  赤ではなく muted の 0.85em で出ていた（実測 `rgb(100,107,121)`）。金銭に直結する唯一の通知経路なので、
  `:not([class])` を付けて class 付きの span には当てないようにした
- 「Pico の button は既定で `width: 100%`」は誤り。2.1.1 で当たるのは `button[type=submit]` だけで、
  この画面のボタンは `type` を持たない（素の button の実測幅は auto）。`width: auto` の上書きは効果が無く、

## 2026-09-05: PR #6 のコードレビュー指摘の修正（決定37・U8）

PR #6 に `pr-code-review` スキルで観点別レビューを行い、ユーザー判断で 11 件を修正した（GitHub には投稿せず、この場で修正）。

### 中核: 支出上限が上限として機能していなかった

レビューで AWS の [AgentCore Payments IAM ガイド](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-iam-roles.html) に次の記述があることが分かった。

> Do not include PaymentSession *write* permissions (for example, `CreatePaymentSession`) and `ProcessPayment` in the same role, or the caller can bypass payment limits by creating new sessions with elevated budgets.

決定35 の実装はこの迂回を IAM で許すだけでなく、**アプリが自動で実行**していた。`isSessionRejection` が
`ConflictException: Session limit exceeded` を「セッション起因」と判定し（`payment-session.test.ts` が
その挙動をテストで固定していた）、`x402-payer.ts` がそれを無条件に `renew()` へ流すため、**上限に当たった
支払いがその場で新しい枠を切って成立していた**。決定35 の理由欄が開示していたのは「枠は時間ごとに戻る」
ことまでで、「上限が一度も支払いを止めない」ことまでは意図していなかった。決定37 として、上限超過は
作り直さず失敗させる側に倒した。

ロール分離は行っていない。共有 Lambda 1 つがセッション作成と支払いの両方を実行するため、ロールを分けても
同じ identity が双方を握ることに変わりがなく、分離にならないため。IAM のリソースは `payment-manager/*` に
絞り、構造での分離は U8 として残した。

### 挙動が変わるもの

- **決済後の再 402 を `PaidToolError` にした**（`paid-tool-caller.ts`）。従来は素の `Error` で、
  `buy-html.ts` の `instanceof PaidToolError` を素通りしてツールハンドラまで伝播し、レシート記録

  起きていないが署名は売り手に渡っており、売り手は有効期限内なら後から決済を確定できる。「資金が動いていないから

ライブラリのオプションは docstring ではなく実装（`node_modules/@aws-blocks/bb-kv-store/dist/index.aws.js`）で
意味論を確かめるべきだった。読めた記録があるときだけ `ifValueEquals` を付ける形に直し、

### 調査で分かった重要事実

- AWS Blocks は AWS 公式（2026-06-16 に public preview 公開、`docs.aws.amazon.com/blocks` に devguide）。
  devguide は Amplify を「補完関係（Amplify = hosting / CI/CD / マネージド体験、Blocks = IfC）」と位置づける
- `BlocksBackend.create()` は devguide「Integrating with existing infrastructure」Pattern 1 の公式 API。
  `@aws-blocks/core` 0.3.1 の `blocks-backend.ts` は `fullId` の説明で「Amplify Gen2 の
  `backend.createStack('blocks')` のネストスタック」を想定ケースとして明記している
- 公式 CLI `@aws-blocks/create-blocks-app` 0.1.21 には `templates/amplify/` があり、`amplify/backend.ts` を
  検出すると `amplify/blocks.ts`・`createBlocksBackend`・`NODE_OPTIONS="--conditions=cdk"` 付きの

  既に Blocks で作ったプロジェクトには当てられない。今回の実装はこの生成物を写した

  `cdk deploy --app="npx tsx -C cdk aws-blocks/index.cdk.ts"`）も案内している。今回は一元管理の要望で
  Amplify 主体（ネストスタック）を採った
- ブラウザの Blocks クライアント（`@aws-blocks/core` `client/index.js`）は API の URL を
  「`{ url }` 指定 → SSR の環境変数 → Node の `.blocks-sandbox/config.json` → ブラウザは同一オリジンの

  相対 URL（`/aws-blocks/api`）を書いた config.json を配り CloudFront で API をプロキシするが、

- Amplify のルートスタック名は `amplify-<namespace>-<name>-<type>-<hash10>`。sandbox は
  namespace = `package.json` の name（英数字のみ、`agentapp`）、name = `--identifier`（既定は OS ユーザー名）。

### 事故: タイムアウトで決済後に諦め、LLM が自動再試行して二重に支払った

  LLM は「失敗」と見て自動で再購入した

- **対処**: GET は SDK へ渡さず 405（Allow: POST, DELETE, OPTIONS）を返す。加えて
  万一ストリーミング応答が来ても待ち続けないよう `isStreamingResponse` で防護し、
  body を cancel して 500 を返す。両方をテストで固定（決定22 に追記）

決済フロー自体は最初から成功しており、この不具合は副次的な GET 経路にのみ現れていた。
